## SECURITY-001: cross-shop data exposure on shared devices via un-scoped client caches surviving logout
**Symptom:** On a device shared between an owner and a teller (the spaza norm), after one user logs out and another logs in, the new user can briefly see the previous user/shop's cached data (products, stock, settings, tellers, sales snapshots) before the background revalidate replaces it. Surfaced while investigating the BUG-052 "owner shows the teller's profile" report — same root cause, broader scope.
**Root cause:** The Phase 44b cache-first stack caches shop-scoped data on the device keyed by ENDPOINT, not by user, and nothing cleared it on sign-out: (1) `useCachedData` writes `localStorage` snapshots under `mvs_cache:<endpoint>`; (2) the service worker SWR-caches `/api/*` GETs under user-less URLs; (3) IndexedDB caches `products`/`cart`/`settings`/`tellers`; (4) the chrome identity mirror + the settings-page snapshot live in `localStorage`. `signOut()` only dropped the Supabase session + (post-BUG-052) the identity mirror. So all the above survived into the next session and painted instantly (synchronous reads) before revalidation.
**Severity:** Moderate — **not a server-side breach.** RLS still blocks fetching NEW cross-shop data; this is a transient display of data already cached on the device, and only on a shared/repurposed device after a user switch. But it's a POPIA confidentiality/data-minimization gap that scales with the user base, and converting more pages to cache-first would widen it.
**Fix (2026-06-04, SW v84 → v85):** New `clearSessionCaches()` ([src/lib/offline/clear-session-cache.ts](src/lib/offline/clear-session-cache.ts)) purges, on sign-out and on a detected user switch: all `mvs_cache:*` localStorage snapshots + the identity mirror + settings/teller/active-teller keys; the IndexedDB `products`/`cart`/`settings`/`tellers` stores via new `clearShopDataCaches()` ([db.ts](src/lib/offline/db.ts)); and every cached `/api/*` response across all Cache Storage versions. Wired into `LogoutButton` + `SwitchUserButton` (awaited before redirect) and `AppChrome.resolve()` on the userId-mismatch branch (covers a silent token-swap with no explicit logout). **Deliberately preserved:** the IndexedDB `pending_sales` queue (clearing it would lose unsynced sales — a separate accepted edge), language preference, and the `mvs_recent_users_v1` Switch-User feature.
**Prevention rule:** Any client-side cache (localStorage/sessionStorage snapshot, service-worker-cached user-scoped GET, or IndexedDB store) that holds shop/user-scoped data MUST be either keyed by `userId`/`shopId` OR purged on every sign-out and user switch. RLS protects the SERVER, not data already written to the device — on shared hardware (which spaza shops use), un-scoped client caches are a cross-tenant leak. Before converting any further page to cache-first, confirm its snapshot is covered by the `clearSessionCaches()` purge (the `mvs_cache:` prefix covers all `useCachedData` keys automatically; bespoke localStorage keys must be added to the exact-key list).

## BUG-052: Post-App-Shell cluster — notification sheet traps nav, owner shows teller's name, checklist buzzer hangs + double-completion
**Symptoms (4, reported together after the App Shell rollout):**
1. Opening the notification bell, then tapping a bottom-nav tab, "stays in notifications" — the only way out is the sheet's back button.
2. Log in as teller → request access → log in as owner → grant: the chrome (name/role area) shows the **teller's** profile until a manual reload.
3. Tapping the daily-checklist buzzer "endlessly loads until you reload manually".
4. The app made the owner "complete the daily checklist twice today".

**Root causes:**
1. **Stacking context.** The `NotificationBell` sheet is `fixed inset-0 z-[70]` but it renders *inside* `TopAppBar` (`sticky top-0 z-30` → its own stacking context). So `z-[70]` is scoped under TopAppBar's z-30, and `BottomNav` (root-level `z-40`) paints **over** the sheet — its tabs stay tappable. Navigating left `isOpen` true (the layout/TopAppBar persists across in-app navs), so the sheet lingered over the new page.
2. **User-less caches.** The `mvs_shell_identity` localStorage mirror wasn't tied to a user, and `/api/tellers/me` is SW-cached (SWR) under a user-less URL. After a teller→owner switch the chrome painted from the teller mirror AND the owner's `/api/tellers/me` fetch was served the teller's stale cached row. Only a reload (eventually) revalidated it.
3. **No fetch timeout.** The checklist page's `fetch('/api/daily-checklist')` had no timeout; on a half-awake radio it hangs and `loading` never clears → infinite spinner.
4. **Date-less SWR key.** `/api/daily-checklist` is in the SW's `SWR_GET_PATHS`, but its payload is date-specific and the cache key had no date — so on a new day the SW could serve yesterday's "empty form" snapshot, prompting a re-fill (the felt "completed twice"; the DB upsert keeps a single row).

**Fix (2026-06-04, SW v83 → v84):**
1. Render the sheet through `createPortal(…, document.body)` so it escapes TopAppBar's stacking context and truly covers the bottom nav (tabs no longer visible/tappable — back button only, as requested). Plus an auto-close on `pathname` change as defence in depth.
2. Tag `ShellIdentity` with `userId`; on resolve, reset the mirror when `session.user.id` differs (teller→owner switch) so the previous person's name/role never lingers. Fetch `/api/tellers/me?u=<userId>` so the SW caches per-user (no cross-user leak). Clear the mirror on sign-out (`clearShellIdentity()` in LogoutButton + SwitchUserButton).
3. Time the checklist fetch out (`AbortController`, 12s) → falls to the existing retry screen instead of spinning forever.
4. Key the checklist fetch URL by today's SAST date (`?d=<date>`) so each day gets a fresh SW entry while same-day reopens stay instant. The SW caching design is untouched (no path removed from `SWR_GET_PATHS`).

Also (same pass, #5 of the report — slow + "error, try again" flash on `/sales`): the sales hub was the one read page still on the network auth guard `getShopAuth()` (a blocking `getUser()` RTT that throws on a sleeping radio). Switched to the Phase 45e read pattern `getShopAuthFast()` (local JWT verify, no network) — faster first paint + one fewer resume-throw point; RLS still the data boundary. **Honest scope:** the streamed Suspense cards still need the radio, so a transient resume error can still hit the auto-recovering `(app)` error boundary; the complete cure is converting the sales hub to client cache-first (deferred — launch-critical UI, its own focused phase).

**Prevention rules:**
- A full-screen overlay must not be rendered inside a `sticky`/`fixed` ancestor that has its own `z-index` (a stacking context) — its z-index can't beat siblings of that ancestor. Portal overlays to `document.body`, or hoist them above all fixed chrome.
- Any client cache (localStorage mirror OR a SW-cached user-scoped endpoint) that can outlive a user switch MUST be keyed/scoped by `userId` (or cleared on sign-out) — otherwise the next user sees the previous user's data until a reload.
- Every client `fetch` that gates a `loading` state needs a timeout; on mobile a suspended radio makes an un-timed fetch hang forever.
- Never SW-cache a date-(or otherwise context-)specific payload under a key that omits that context — bake the discriminator into the URL.

## BUG-051: Dashboard "something went wrong" on resume-from-background (App Shell Stage 2 follow-up)
**Symptom:** After the App Shell Stage 2 work, the app is fast and resume is smooth — EXCEPT navigating to the **dashboard** after a long background (e.g. switching back from YouTube) shows "something went wrong / app hit an unexpected error". Other tabs (e.g. Sales) work fine.
**Root cause:** Stage 2 made `/sale` (and `/`) data-free + SW-cached, so they paint from cache with no server render on resume. The **dashboard is the one remaining route still server-rendered with the owner's data**, so navigating to it (or `DashboardAutoRefresh`'s `router.refresh()`) re-runs Server Component queries. On a resume the radio is still waking / the token just expired, so a **raw fetch rejection** from the page-level `business_documents` + `owner_profiles` (+ `municipalities`) reads rejected the `Promise.all` and threw the whole page into the `(app)` error boundary. `getShopForRequest` already caught its own rejection; these three did not. (The Suspense cards — ComplianceCard / JourneyProgressCard / LatestSales / TodaySummary — already `try/catch → null`, so they weren't the culprit.)
**Fix (2026-06-02):** Wrap the three unguarded dashboard reads with `.then((r) => r, () => ({ data: null }))` (the same degrade-don't-crash pattern the `(app)` layout uses for its tellers read). Worst case is now an empty card that `DashboardAutoRefresh` revalidates once `RESUME_READY` confirms the connection is back — never the error screen. SW v79 → v80.
**Proper fix — SHIPPED (2026-06-02, commit d22226a):** `/dashboard` is now fully data-free + client cache-first (new `GET /api/dashboard` payload + presentational client card views; the page renders from one cached snapshot). It no longer server-renders on resume at all, so this class of error is now structurally impossible there. The degrade-don't-crash wrapping above stays as defence in depth. (The interim degrade fix preceded the proper fix; both are in the tree.)
**Prevention rule:** Every Server Component data read on a route reachable via resume/`router.refresh` MUST degrade on a raw fetch rejection (catch → null/empty), never let it reject a `Promise.all` into the route error boundary. On mobile the radio is regularly asleep on resume; an un-caught Server Component query = a guaranteed "something went wrong" screen.

## BUG-050: Resume-from-background — tapping a tab freezes 2–3 min with no spinner
**Symptom:** After backgrounding the PWA for a long time, returning and tapping a bottom-nav tab loads "extremely slow" — the loading spinner doesn't even appear for a while; it takes ~2–3 minutes to *start* loading. (Distinct from BUG-049's crash/error — this is a silent freeze with no error and no spinner.)
**Root cause:** A bottom-nav tap is a **client-side navigation that fetches an RSC payload** from the server. That fetch has **no timeout and bypasses the service worker** (RSC requests were deliberately excluded from SW caching in BUG-039/BUG-040). With `experimental.staleTimes.dynamic = 30` (and `static = 180`), every tab's cached payload — and its prefetched `loading.tsx` shell — went **stale within seconds of backgrounding**, so every resume tap re-issued the RSC fetch. On a just-foregrounded mid-range Android the network radio is still suspended, so that fetch **sits queued with no response**: the navigation never "commits," so `loading.tsx` never paints (frozen screen, no spinner), and it only unfreezes once the radio wakes / the request finally resolves → the 2–3 min stall. `ResumeGuard` wakes the radio + refreshes the token on resume, but the user taps a tab faster than its probe (≤4s) + refresh (≤8s) finish, so navigation races ahead into the dead radio.
**Fix (2026-06-01):** Widen the client Router Cache lifetimes in `next.config.ts`: `staleTimes.dynamic 30 → 1800`, `static 180 → 1800`. A tab opened earlier in the session now re-opens **instantly from the in-memory Router Cache** on resume — no RSC fetch, no radio dependency — and even a genuinely-needed fetch shows the prefetched spinner instead of a frozen screen. Freshness is preserved out-of-band: cache-first screens (`useCachedData`) revalidate on `RESUME_READY`; mutations force-refresh via `DATA_CHANGED` + realtime; non-converted pages self-heal via `useRefetchOnVisible` → `router.refresh()` on resume — all in the **background**, after `ResumeGuard` confirms connectivity, so none of it blocks the paint. SW v73 → v74.
**Honest scope:** does NOT fix a true cold WebView kill (Android evicts the whole process → no in-memory Router Cache → first paint still needs the network). That's the larger static App-Shell rebuild. This fix only covers the (common) case where the WebView stayed alive in the background.
**Prevention rule:** In an authenticated App-Router PWA, client-side navigations issue un-timeoutable RSC fetches that bypass the service worker — so the in-memory Router Cache (`staleTimes`) is the ONLY thing standing between a resume tap and a dead-radio hang. Keep `staleTimes.dynamic`/`static` generous (minutes, not seconds) and rely on event-driven background revalidation (`RESUME_READY` + `DATA_CHANGED` + realtime) for freshness, rather than short cache windows that force a blocking server round-trip on every resume.

## BUG-049: Resume-from-background crash + slow cold open — root-cause fix (Phase 44a, supersedes the BUG-048 band-aid)
**Symptom:** Same as BUG-048 but persisting after that fix: resuming the backgrounded PWA still showed "we ran into a problem", tapping a tab after background sometimes wouldn't load (felt *worse* after BUG-048), and cold open could take ~15s. User pushed for a real fix, not symptom-treatment.
**Root cause:** Every authenticated render ran `supabase.auth.getUser()` — a **network round-trip to the Supabase auth server** — in `(app)/layout.tsx` (and `dashboard/page.tsx`) on *every* navigation, *and* `router.refresh()` fired on raw `visibilitychange`/`focus`/`pageshow`. On a mid-range Android resuming from background the radio is still suspended and/or the access token expired while backgrounded, so that auth call (and the Server-Component DB queries behind it) hung or threw → the `(app)` error boundary, or the RSC fetch failed → Next falls back to a hard reload that hangs (Next.js #53813/#60549). Supabase's client can also desync after a long tab suspension (supabase/supabase#36046). BUG-048's 600ms-defer was a band-aid over the same network-on-resume mechanism.
**Fix (Phase 44a):**
- **`getUser()` → `getClaims()`** via new `lib/auth/claims.ts::getAuthClaims()` in the layout + dashboard. `getClaims()` verifies the JWT **locally (WebCrypto, no network)** once asymmetric JWT signing keys are enabled in Supabase — so a valid token renders the shell instantly even on a dead radio. Until keys are enabled it transparently falls back to a network verify (no regression), and on a transient failure `getAuthClaims` degrades to the local cookie session (`getSession()`) for render-only gating. **RLS + per-route `getShopAuth()`/`requireAdmin()` (still `getUser()`) remain the data-layer security boundary.**
- **`ResumeGuard`** (`components/ResumeGuard.tsx`, mounted in the app layout): on resume it confirms connectivity (HEAD probe to `/manifest.json`), refreshes the Supabase session if the token is near expiry (racing an 8s timeout), and only THEN broadcasts a new `RESUME_READY` event.
- **`useRefetchOnVisible` now listens to `RESUME_READY`** instead of raw visibility events, so a passive `router.refresh()` only fires after the connection is confirmed up and the session is fresh. `DATA_CHANGED` (mutations) still fires immediately.
- **Degrade-don't-crash:** `getShopForRequest` catches a raw network rejection → returns null (the React.cache'd value stays safe for every dashboard reader); the layout's tellers read degrades to a nameless shell.
- **`experimental.staleTimes.dynamic = 30`** so idle tab back-and-forth reuses the client Router Cache instead of re-hitting the server.
**Honest scope:** cold open is faster (one fewer auth RTT, gated resume) but not instant — the authed HTML still needs the network on a true cold start. Full instant-open (cached data-free shell + SW-served HTML, per screen) is Phase 44b. The resume crash fix is *partial until asymmetric JWT keys are enabled* — with them, auth verification is fully local and never touches the network on resume.
**Prevention rule:** In an authenticated PWA, never put a network auth call (`getUser()`) on the per-navigation render path — verify the JWT locally with `getClaims()` (+ asymmetric keys) and keep `getUser()` only on API routes where a fresh server-validated user is required. Never fire `router.refresh()`/refetch off a raw resume event — gate it behind a single resume coordinator that confirms connectivity + refreshes the session first. Server Components that depend on the network must degrade to a shell, never throw into the route error boundary.

## BUG-048: "Unexpected error" + dead-tap slowness on resume-from-background
**Symptom:** Returning to the PWA after it sat in the background (user was in WhatsApp etc.) sometimes showed the `(app)/error.tsx` screen ("The app hit an unexpected error. Your sales and stock data are safe."), and tabs felt unresponsive — you could tap several times before anything happened.
**Root cause:** On resume, `useRefetchOnVisible` consumers (notably `DashboardAutoRefresh`'s `router.refresh()`) fired **synchronously** on the `visibilitychange`/`focus`/`pageshow` events — while Android still had the radio suspended and/or the Supabase access token had expired in the background. The resulting RSC re-render ran Server Components whose Supabase queries threw on the dead/mid-wake connection, bubbling to the `(app)` error boundary. RSC payload fetches also deliberately bypass the service worker (no offline fallback, no timeout — see `sw.js`), so a failed refresh had nowhere soft to land. The refresh storm also contended with the waking radio, making real navigations feel dead.
**Fix:** (a) `useRefetchOnVisible` now **skips passive refreshes while `navigator.onLine === false`** and **defers them by a ~600ms settle window** so the refresh doesn't race the waking radio (DATA_CHANGED mutations still fire immediately). (b) `(app)/error.tsx` is now **self-healing**: on a transient error it auto-calls `reset()` — after the `online` event if currently offline, or after a 1.2s beat if online — with a 10s `sessionStorage` throttle so a genuinely-persistent error retries once then falls through to the manual "Try again" screen instead of looping.
**Prevention rule:** Never fire `router.refresh()` or a network refetch synchronously on a visibility/focus/resume event — gate it on `navigator.onLine` and a small settle delay, because the mobile radio is often still asleep at that instant. For an authenticated PWA where RSC fetches bypass the SW, treat the route error boundary as recoverable: auto-retry transient failures (throttled) rather than showing an alarming screen for what a reload fixes.

## BUG-001: /onboarding blocked for unauthenticated users
**Symptom:** Clicking "Create your shop" on the login page reloaded the login page instead of opening onboarding.
**Root cause:** `/onboarding` was not listed in `PUBLIC_ROUTES` in `src/middleware.ts`. Unauthenticated users were redirected to `/login` before the page could render.
**Fix:** Added `/onboarding` and `/api/onboarding` to `PUBLIC_ROUTES`.
**Prevention rule:** Any page that must be reachable before login (signup, onboarding, password reset, etc.) MUST be added to `PUBLIC_ROUTES` in middleware. Always check this list when creating new pre-auth pages.

## BUG-002: Missing /auth/callback route — "localhost error" after email confirmation
**Symptom:** After clicking the Supabase email confirmation link, the user was redirected to `localhost:3000/auth/callback` which returned a 404/error page.
**Root cause:** Supabase redirects to `{site_url}/auth/callback?code=xxx` after email confirmation. The app had no handler at this path to exchange the code for a session.

**Prevention rule:** Any new Supabase project MUST have an `/auth/callback` route. Any auth flow that uses email links (confirmation, magic link, password reset) relies on this route. Never remove it.

## BUG-004: /api/sales missing authentication check
**Symptom:** The POST /api/sales endpoint accepted requests from unauthenticated callers. Any request with a valid JSON body could complete a sale and decrement stock.
**Root cause:** Auth check (`supabase.auth.getUser()`) was never added to the route handler. RLS on the database would have blocked data writes, but the API layer should fail fast before hitting the DB.

## BUG-008: Redirect loop — authenticated user with no role bounces between /onboarding and /dashboard
**Symptom:** Browser shows "redirected too many times" when a user has an auth session but hasn't completed onboarding.
**Root cause:** Proxy redirected any authenticated user away from public routes (including `/onboarding`) to `/dashboard`. Then at `/dashboard`, seeing no role, it redirected back to `/onboarding`. Infinite loop.

## BUG-009: POST /api/onboarding redirected away — shop setup silently fails
**Symptom:** Step 2 of onboarding (shop setup) hangs on "Creating your shop..." and nothing is saved to Supabase tables.
**Root cause:** Proxy guard for onboarding only matched `pathname.startsWith('/onboarding')` but the API call goes to `/api/onboarding`. An authenticated user with no role hitting `/api/onboarding` was redirected to `/dashboard` instead of being allowed through.

**Prevention rule:** When adding a guard exception for a page route, always check if there's a corresponding `/api/` route that also needs the exception. Page routes and their API counterparts must be treated as a pair.

## BUG-010: Hydration mismatch on sale page — OfflineBanner differs between server and client
**Symptom:** React error "Hydration failed because the server rendered HTML didn't match the client" on `/sale`. Server renders `<main>`, client renders `<div className="bg-amber-500...">` (OfflineBanner).
**Root cause:** `useOnlineStatus` initialized `useState` with `navigator.onLine` — on the server, `navigator` is undefined so it defaults to `true` (banner hidden). On the client, `navigator.onLine` can be `false` (banner shown), causing a mismatch.
**Fix:** Always initialize `useState(true)` and read the real `navigator.onLine` value in `useEffect` after hydration.
**Prevention rule:** Never use browser-only APIs (`navigator`, `window`, `document`, `localStorage`) in `useState` initializers. Always default to a server-safe value and sync in `useEffect`.

## BUG-013: Adding stock with partial expiry dates drops untracked units
**Symptom:** User adds 10 units, assigns 5 to an expiry date. Only 5 units are added to stock instead of 10.
**Root cause:** In `stock/[id]/page.tsx` `handleSubmit`, when `trackAddExpiry` is true, the code only creates batches via `/api/batches` (which each increment stock by their quantity) then returns early. Units not assigned to any expiry entry are silently dropped.
**Fix:** After creating all expiry batches, calculate `remainder = parsedAmount - totalAdded`. If remainder > 0, call `/api/stock` to add the untracked units via regular stock adjustment.
**Prevention rule:** When a form has a "total quantity" field and a subset breakdown (e.g. expiry entries), always verify the subset sums to the total. If it doesn't, handle the remainder explicitly — never assume the subset covers everything.

## BUG-012: admin_payments table had RLS disabled — defense-in-depth gap
**Symptom:** `admin_payments` was the only table without RLS enabled. While access was gated by `requireAdmin()` in the API layer and the service role client, a bug in application code could have exposed all payment records via the anon/authenticated client.
**Root cause:** Original migration (006) explicitly skipped RLS with comment "no RLS needed" — prioritized convenience over defense-in-depth.
**Fix:** Added `ALTER TABLE admin_payments ENABLE ROW LEVEL SECURITY;` to migration 006. No policies added — with RLS on and zero policies, anon/authenticated clients get 0 rows. Service role bypasses RLS automatically.

## BUG-018: Barcode scanner fails on small/dense barcodes — minimum focus distance, not autofocus
**Symptom:** Scanner decodes large barcodes fine but fails on small/dense ones (typical EAN-13 on single sweets, snacks, small SA grocery items). Reported on a Galaxy S25 — top-tier optics, so camera quality wasn't the cause.
**Root cause:** Two compounding issues. (1) Modern Android flagships (incl. S25) have a **minimum focus distance of ~10–15 cm on the main rear camera**. Users instinctively hold the phone close (3–5 cm) to make a small barcode fill the frame, but that's *inside* the lens minimum — the image blurs and never resolves. Hardware barcode scanners use cheap fixed-focus optics tuned to that exact range, which is why they don't have this problem despite worse cameras. (2) [src/hooks/useScanner.ts](src/hooks/useScanner.ts) used `decodeFromVideoDevice` with no format hints, so ZXing scanned every supported 1D + 2D format on every frame at default tolerances — slow path, low success on imperfect images.
**Fix:** Three layered changes in [src/hooks/useScanner.ts](src/hooks/useScanner.ts) + [src/components/scanner/BarcodeScanner.tsx](src/components/scanner/BarcodeScanner.tsx). (a) `BrowserMultiFormatReader` now constructed with `DecodeHintType.POSSIBLE_FORMATS = [EAN_13, EAN_8, UPC_A, UPC_E, CODE_128, CODE_39, QR_CODE]` (SA retail's actual barcode mix) plus `TRY_HARDER = true` — restricting formats lets the decoder run a more aggressive path per frame. (b) `decodeFromConstraints` requests `1920x1080 @ focusMode: 'continuous'`. (c) After the stream is live, feature-detects `track.getCapabilities().zoom` and **auto-applies 2× hardware zoom** so users can keep the phone at proper focus distance (15 cm) while a small barcode still fills the frame. The scanner UI also gains pinch-replacement +/− zoom controls (rendered only when the track exposes hardware zoom) and tap-to-focus (`pointsOfInterest` advanced constraint, feature-detected). **Prior attempt** (commit `4cc0c3a`) wired `getUserMedia` manually and handed the stream to `decodeFromStream` — broke scanning entirely because `decodeFromStream` re-attaches the stream and awaits `loadedmetadata`, which never fires on a pre-attached `<video>`. Corrected by `bf9b2c1`. **Prior diagnosis** ("camera doesn't autofocus") was also wrong: continuous AF was on, but AF can't focus inside the lens minimum.
**Prevention rule:** When a user reports "camera-won't-focus" on a high-end Android phone, **don't blame autofocus** — first check whether they're inside the lens minimum focus distance (~10–15 cm on flagship main sensors). Solution is hardware zoom, not closer phone. For machine-vision via `getUserMedia`: (1) always restrict ZXing to the formats you actually need + `TRY_HARDER` — full-format scanning is slow and brittle. (2) Always request HD + `focusMode: 'continuous'` in constraints; defaults prioritise framerate, not detail. (3) Always feature-detect `track.getCapabilities()` before applying `zoom`/`focusMode`/`pointsOfInterest` advanced constraints — Safari throws on unsupported names. (4) Use `decodeFromConstraints` and let ZXing own stream attachment; do not pre-set `videoEl.srcObject` then call `decodeFromStream` (double-attach hangs on `loadedmetadata`).

**Follow-up (2026-05-06):** Even with the above, scanning was inconsistent on Android. Researched production scanners (Scandit, html5-qrcode, ML Kit). The bigger architectural problem: ZXing JS is a pure-JS port that takes ~350ms per frame on Chrome benchmarks. Production apps use the native `BarcodeDetector` API (Chrome 83+ on Android) which is hardware-accelerated via Google's ML Kit — same engine inside Google Lens, 5–10× faster, dramatically more accurate. [src/hooks/useScanner.ts](src/hooks/useScanner.ts) now feature-detects `window.BarcodeDetector`, calls `getSupportedFormats()`, and uses native if `ean_13` is supported (covers Chrome Android, Edge Android). Falls back to ZXing on iOS Safari and older browsers. The native path runs a 100ms `setTimeout` decode loop (10fps — Scandit and html5-qrcode defaults; phone cameras don't deliver new in-focus frames faster than that, so 30fps decode just wastes CPU on blurry duplicates) calling `detector.detect(videoEl)` directly. Both paths share `tuneTrack()` for continuous AF + 2× auto-zoom + the 30fps `frameRate` cap. **Additional prevention rule:** for any web-based machine-vision, prefer `window.BarcodeDetector` / `window.FaceDetector` / `window.TextDetector` over JS-port libraries. Always feature-detect with `getSupportedFormats()` before relying on a specific format — Chrome's BarcodeDetector format support varies by device.

## BUG-021: "Add to Home Screen" installs a shortcut with browser chrome instead of a standalone PWA
**Symptom:** Owners reported tapping "Add" from Chrome on Android put a Movestock icon on their home screen, but launching it opened the site inside a Custom Tab with the browser address bar still visible at the top — not the chrome-less standalone experience the brief asked for (ChatGPT-style). Test by `curl -I` against the deployed URL — anything other than 200 OK on these is a bug.

## BUG-030: Barcode scanner accepts partial decodes (only part of barcode captured)
**Symptom:** On `/sale` and the product picker, occasionally a scan would return a shortened barcode (e.g. 11 or 12 digits when scanning a full EAN-13) — the wrong product (or no product) was added to the cart.
**Root cause:** `src/hooks/useScanner.ts` accepted the very first decode from either the native `BarcodeDetector` or ZXing's `BrowserMultiFormatReader`. ZXing's `TRY_HARDER` mode produces partial reads on blurry frames, and neither path validated length or the GS1 mod-10 check digit before firing `onScan(value)`. A single bad frame = a wrong product.
**Fix:** New pure validator `src/lib/barcode/validate.ts` enforces per-format digit-count (EAN-13=13, EAN-8=8, UPC-A=12, UPC-E=6/8) plus GS1 mod-10 checksum. Both scanner paths now require: (a) `isValidBarcode(value, format)` passes, AND (b) the same value appears in **two consecutive frames/callbacks** before firing. The 2-frame confirm adds ~100ms at 10fps (negligible) but eliminates single-frame misreads. Non-numeric payloads (QR codes, alphanumeric Code-128) bypass validation — those decoders are framing-aware and don't produce partial reads. Unit tests in `tests/unit/barcode-scanner.test.ts`.
**Prevention rule:** Any decoded value coming from a hardware sensor/camera/OCR pipeline must be validated before being treated as authoritative. For barcodes specifically: format length + checksum. For continuous-decode pipelines (every frame is a fresh guess), require **N-frame agreement** before acting — never trust a single frame. Never enable `TRY_HARDER` without a corresponding validation layer downstream.

## BUG-033: Chrome "Password Reuse Protection" warning on add-teller form
**Symptom:** When the owner submits the New Teller form, Chrome flashes "you just entered a password on a deceptive site", turns the address bar grey, and shows an X icon. First attempt to fix with `autoComplete="new-password"` did not suppress the warning.
**Root cause:** This is **Chrome Password Reuse Protection** (a.k.a. Password Alert), not a generic autocomplete heuristic. When the owner is signed into Chrome with Sync, Chrome fingerprints every password they save. Typing any of those fingerprinted passwords into an `<input type="password">` on a domain Chrome does **not** know that password belongs to fires the warning at the keystroke level — independent of any `autocomplete` attribute. The owner was setting a teller credential and (consciously or not) typing something close to one of their saved Google/Gmail passwords. `autoComplete="new-password"` only affects autofill and the password manager UI, not Password Reuse Protection.
**Fix:** Eliminated `<input type="password">` from the teller flow entirely. Teller credentials are now **6-digit numeric PINs** entered via `<input type="text" inputMode="numeric" pattern="[0-9]*" maxLength={6} autoComplete="off">`. Chrome's Password Reuse Protection only inspects `type="password"` fields, so it never fires on the PIN input. As a bonus this is better UX for non-technical spaza staff (a PIN is far easier to remember + share than a password) and matches the till-style mental model of the rest of the app. Schema (`createTellerSchema`) tightened to `/^\d{6}$/`; the input strips non-digits and clamps to 6 chars; both the create form (`/tellers/new`) and the login form (`/login` teller tab) are converted. i18n keys `label_password`/`hint_password` and `teller_label_password`/`teller_hint_password`/`teller_error_wrong_password` renamed to `_pin` variants across all 5 locales. Owner email+password login is unchanged (owners don't reuse-warn on their own password).
**Migration note:** Existing tellers were created with arbitrary passwords (likely alphanumeric). The new login form strips non-digits, so they cannot type their old password. Owners must deactivate + re-add affected tellers with a new 6-digit PIN.
**Prevention rule:** Never use `<input type="password">` for an "owner-sets-credential-for-someone-else" flow (admin creating user, owner adding teller, parent setting child's password). The person at the keyboard is overwhelmingly likely to type a password they use elsewhere → Chrome Password Reuse Protection fires → looks like a phishing warning to the user. Use a numeric PIN with `type="text" inputMode="numeric"` instead. The `autoComplete` attribute is necessary but not sufficient — it does not suppress Chrome's password-fingerprint comparison. Reserve `type="password"` for fields where the **owner of the password** is the one typing it (their own signup, their own login).

## BUG-039: Whole app slow — even the loading screen took 1–2 s to appear
**Symptom:** "The app is extremely slow, it even takes long to show the loading screen, its almost unusable." On SA mobile networks (300–500 ms RTT), the dashboard regularly took 3–5 s before any visible chrome appeared, and `loading.tsx` itself was delayed.
**Root cause (compounded — 5 issues):**
1. **`(app)/layout.tsx` did 3 sequential Supabase queries** (shop → tellers → daily_checklists) before any HTML streamed. In App Router, `loading.tsx` only renders after the surrounding layout's awaits resolve — so even the loading spinner was blocked by ~3 RTTs (~1–1.5 s on slow mobile).
2. **`dashboard/page.tsx` then did its own `shop_users → shops` join (waterfall #1) before firing the 3 owner-profile queries (waterfall #2)** — another 2 sequential RTTs on top.
3. **Service worker used `network-first` for HTML navigation** ([public/sw.js](public/sw.js)) — every repeat visit waited for the network even when a perfectly good cached page existed. Worse, it also cached RSC payload requests (`?_rsc=…`) as navigation HTML, producing content-type mismatches on client-side router pushes.
4. **3 Google Fonts preloaded on every page** (Plus Jakarta + Noto Sans Ethiopic + Noto Nastaliq Urdu) — `next/font/google` injects a `<link rel="preload" as="font">` for every declared font. Nastaliq Urdu alone is ~500 KB. Latin users downloaded ~650 KB of script-glyphs they would never render.
5. **23 i18n namespaces eagerly loaded** via dynamic `import()` after hydration — 23 separate JS chunk requests on every first paint, leaving `useTranslation()` returning raw keys until the chunks landed.
**Fix:**
1. Collapsed the 3 layout queries into one `Promise.all` — 3 RTTs → 1.
2. Dashboard now reads `role` + `shopId` from `user.app_metadata` (already validated by middleware), drops the `shop_users` join, and fires `shops` + `business_documents` + `owner_profiles` in one parallel batch — 2 waterfalls → 1.
3. SW navigation strategy switched to `stale-while-revalidate`. Document-only check (`request.destination === 'document'` and not an `_rsc=` payload) prevents caching RSC chunks. Cache bump v31 → v32.
4. Added `preload: false` to the two non-Latin fonts. CSS rules stay (so `:lang(am)` / `:lang(ur)` still pick them up if the user is on those locales), but the `<link rel="preload">` is gone for everyone else.
5. `(app)/layout.tsx` now pre-loads the full app-shell namespace map server-side via `loadNamespacedTranslations()` and passes it to `<LanguageProvider initialNsMap={…}>`. New `initialNsMap` prop seeds React state directly, so the client-side `useEffect` fetch is skipped on first paint and only fires when the user actually changes locale at runtime. 23 chunk requests → 0.
**Prevention rule:** Three rules in one — (a) every `await` in a layout / page that does N independent queries MUST use `Promise.all` instead of sequential awaits, because each one delays `loading.tsx` from appearing; (b) `next/font/google` declarations for scripts only some users need MUST set `preload: false` — the CSS rule keeps the font available, only the eager preload is dropped; (c) when a server component pre-computes data a client provider would otherwise fetch, pass it as an `initial*` prop and skip the client fetch — the RSC payload is gzipped HTML, which is cheaper than N separate HTTP/2 requests on mobile.

## BUG-040: BUG-039 regressions — pages "refuse to load", checklist FAB missing on cold open, locale waterfall reintroduced
**Symptom:** Three compounding regressions after BUG-039 shipped:
1. "Takes ages to load when opening it" — first paint *slower* than before, not faster.
2. "Doesn't show the checklist buzzer until you click something on the dashboard" — the amber checklist FAB was absent on first paint, then appeared after any client-side navigation.
3. "Sometimes when you click on a page it just refuses to load it" — navigations stalled indefinitely.
**Root cause (3 issues):**
1. **Service worker `stale-while-revalidate` for navigation HTML is unsafe for an authenticated app.** [public/sw.js](public/sw.js) precached `/sale`, `/login`, `/dashboard`, `/settings` on install. The cached HTML referenced build-specific `_next/static/chunks/...` URLs. After the next cache-bump deploy, the cached HTML was served but the chunks were gone → browser stalled fetching dead chunks. Additionally, the precache fetch of an auth-protected route while logged out captured a 307→/login response under the original URL, so even logged-in users could be served the login page from cache. And per-user data baked into the cached HTML (shop name, locale strings, today's checklist state) became stale across days and across users on the same device.
2. **`ChecklistReminderFab.recheck` only ever HID the FAB.** [src/components/ChecklistReminderFab.tsx](src/components/ChecklistReminderFab.tsx) had `if (completed) setVisible(false)` — no path back to visible. When SW served stale HTML where `initialVisible=false` (e.g. cached yesterday after the owner completed the checklist), today's pageshow recheck returned `completed=false` but the FAB stayed hidden. Only a `router.push` (which re-renders the server layout with fresh data and re-mounts the FAB with a new `initialVisible`) could surface it.
3. **`loadNamespacedTranslations` was awaited sequentially after the supabase batch in `(app)/layout.tsx`** because it depended on `shop.language`. Three sequential awaits (auth → supabase batch → i18n) → loading.tsx blocked until all three resolved.
**Fix:**
1. SW navigation reverted to **network-first with `/offline.html` fallback**. `PRECACHE_URLS` stripped to `['/offline.html']` only — authenticated routes are NEVER precached now. Navigation HTML is NEVER cached (RSC payload + Next.js router prefetch are the fast path for repeat visits, not stale HTML). Cache bump v34 → v35.
2. `ChecklistReminderFab.recheck` now does `setVisible(!completed)` (bidirectional) and runs once on mount via `useEffect` so it self-heals from any stale `initialVisible` without waiting for a visibility/focus event.
3. **Locale moved to a server-readable cookie** (`mvs_locale`, `Path=/; SameSite=Lax; Secure (prod); Max-Age=1y; NOT httpOnly` — locale isn't a security boundary). `(app)/layout.tsx` and `(auth)/layout.tsx` read the cookie synchronously and fire `auth.getUser()` + `loadNamespacedTranslations(localeFromCookie)` in one `Promise.all`. Shop record remains the durable source of truth: if the cookie is missing, the layout reconciles against `shop.language` after the parallel batch and `LanguageProvider` writes the cookie client-side on mount. Cookie write paths: `LanguageProvider.setLocale` (on language change), `/api/onboarding` (Set-Cookie on shop creation), `/api/auth/teller-login` (Set-Cookie based on shop.language).
**Prevention rule:** Three rules — (a) **NEVER precache auth-protected routes in a service worker**; they capture either a redirect (logged-out install) or one user's snapshot (logged-in install), both of which poison every later request on that device. Precache only routes that are truly stateless (e.g. `/offline.html`). (b) **NEVER use `stale-while-revalidate` on navigation HTML in an authenticated PWA.** The HTML contains per-user data, locale-specific strings, and build-specific chunk hashes — all three become incorrect on a stale serve. The fast path for repeat visits is the Next.js router prefetch + RSC payload, NOT cached HTML. (c) **Client state hints from the server (`initialVisible`, `initialNsMap`, etc.) MUST be reconciled with a fresh fetch on mount when the underlying data changes faster than the cache TTL.** A "stale=hidden" rule needs a path back to visible.

## BUG-041: Tellers list (and other SWR-cached lists) doesn't refresh after add/remove
**Symptom:** After adding a new teller via `/tellers/new`, the user is returned to `/tellers` but the new teller doesn't appear in the list. Removing a teller has the inverse problem — it stays visible. Same regression applies to any list whose endpoint is in `SWR_GET_PATHS` (products, suppliers, business documents, etc.) — first read after a mutation shows the pre-mutation snapshot.
**Root cause:** `/api/tellers` is in [public/sw.js](public/sw.js)'s `SWR_GET_PATHS`, so the service worker serves a cached response immediately on every GET and only refreshes the cache in the background. When the mutation flow ran:
1. `POST /api/tellers` (or `PATCH /api/tellers/:id`) — mutation succeeded at the server.
2. `emitDataChanged()` fired before the next page mounted, so the in-tab listener didn't catch it.
3. `router.push('/tellers')` — page mounted, `useEffect` ran `load()` which called `fetch('/api/tellers', { cache: 'no-store' })`.
4. The SW intercepted that GET and returned the **pre-mutation cached response** synchronously; the background revalidation updated the cache, but only after the UI had already rendered the stale list.
The client's `cache: 'no-store'` only bypasses the **browser HTTP cache** — it doesn't tell the service worker to skip its own cache. And the SW had no signal that the preceding mutation invalidated the GET.
**Fix:** Added a cache-invalidation branch to the SW's `fetch` handler: for any non-GET request whose pathname matches (or is a sub-path of) any entry in `SWR_GET_PATHS`, every cached entry for that base path is deleted via `cache.delete(req)` inside `event.waitUntil`. The mutation still passes through to network. The next GET on that path therefore misses the SW cache and goes to network, returning fresh data on first render. Cache bump v35 → v36. Applies automatically to all six SWR-cached endpoints (tellers, products, settings, suppliers, business-documents, compliance-score, daily-checklist) — fixes the same latent bug everywhere without per-page wiring.
**Prevention rule:** When a service worker serves a GET endpoint with a stale-while-revalidate strategy, any same-origin mutation on the SAME base path (incl. sub-paths like `/api/foo/:id`) MUST invalidate the SW cache entry for the GET. Otherwise the SPA's "POST → navigate → GET" flow renders the pre-mutation snapshot on first paint. A `cache: 'no-store'` fetch option does NOT bypass the service worker — only the browser HTTP cache. Defence-in-depth: any time you add an endpoint to `SWR_GET_PATHS`, audit the matching mutation endpoints and confirm the invalidation pattern covers them.

## BUG-045: Cost-optimisation regressions — buzzer stale, app loads endlessly, removals missing from history
**Symptom:** Three issues reported after the 2026-05-24 Vercel + Supabase cost-optimisation pass. (1) The daily-checklist buzzer (the amber pulsing FAB) took several seconds to appear when needed and kept showing for several seconds after the checklist was saved. (2) On a cold open the screen "loaded endlessly until I tap on the screen again, and even then it takes so long". (3) Stock removed via the Stock detail "Remove stock" mode on `/stock/[id]` did not appear under `/stock-take/history` — the page showed only counts done via `/stock-take`.
**Root cause:**
1. The cost pass expanded the service worker's stale-while-revalidate cache to include `/api/daily-checklist/status`. The route deliberately sends `Cache-Control: no-store` because the FAB depends on fresh status to clear immediately on save and to flip on a new-day rollover — but the SW honours its own `SWR_GET_PATHS` list, not the response header, and cached the response anyway. Compounding this, BUG-041's mutation-invalidation logic only cleared cache entries whose pathname **exactly** matched the mutated path. POST `/api/daily-checklist` therefore invalidated the cached `/api/daily-checklist` GET but NOT the cached `/api/daily-checklist/status` GET — they're separate cache entries — so the FAB's recheck still served the pre-save snapshot. The 10 s `useRefetchOnVisible` passive throttle (also from the cost pass) then gated the next opportunity for a fresh read.
2. The SW navigation handler was `fetch(request).catch(...)` with no timeout. On Android, when the radio is suspended by battery-save heuristics, `fetch()` does not reject — it hangs until a user interaction (the "tap on the screen") wakes the radio. The user-perceived behaviour is a blank screen that suddenly springs to life on tap. This isn't new to the cost pass, but became more noticeable now that the SW serves more requests.
3. `getStockTakeHistory` reads only `stock_take_entries`. The Stock detail page's Remove flow writes to `stock_adjustments` (`adjustStock()`). Two separate audit tables with no merging in the reader.
**Fix:**
1. Removed `/api/daily-checklist/status` from `SWR_GET_PATHS` in [public/sw.js](public/sw.js) — it's a tiny `{ completed: bool }` payload, caching saves nothing meaningful and the staleness causes UX bugs. Generalised mutation invalidation so a POST/PATCH on path P clears every cached entry whose pathname equals P **or starts with `P + '/'`** — so a future POST `/api/X` clears `/api/X`, `/api/X/status`, `/api/X/history` in one sweep. SW cache v56 → v57.
2. Added a 15 s timeout race to the SW navigation handler — if the underlying `fetch()` hasn't resolved by then, fall through to the cached `/offline.html` (the user reloads instead of staring at a blank screen). Fast networks are unaffected; slow networks still get their response when ready as long as it's under 15 s.
3. [stock-take-history.ts](src/lib/db/stock-take-history.ts) now merges `stock_take_entries` and `stock_adjustments` into one chronological session list. Tellers are resolved for adjustments by looking up `tellers.user_id = stock_adjustments.adjusted_by` (no FK between the two tables — they both reference `auth.users.id`). Three parallel reads, capped at 500 combined rows after merge. The pure `shapeStockTakeHistory()` is unchanged so existing unit tests still pass.
**Prevention rule:** (a) When adding an endpoint to a service-worker SWR cache list, check the route handler — if it sends `Cache-Control: no-store`, that's a hard signal "do not cache me" and the SW must honour it (omit from SWR_GET_PATHS). The header was put there for a reason. (b) Service-worker mutation invalidation must clear the mutated path AND all cached sub-paths of it — a single `/api/X` POST routinely affects `/api/X`, `/api/X/status`, `/api/X/history`, `/api/X/me` etc., and they must all go. (c) Every `fetch()` in a service worker that intercepts navigation MUST have a timeout race — `fetch()` does not reject on a stalled radio, it hangs forever. (d) When a single domain event can be recorded into multiple audit tables (here: every stock change → either `stock_take_entries` or `stock_adjustments`), the reader for "show me every event" MUST merge across all source tables; never let the UI page name a single table or a single screen — name the domain.

## BUG-046: False "You're offline" banner + slow-load page mislabelled as offline + freezer temp can't go negative
**Symptom:** Three issues reported. (1) The thin offline banner showed "You're offline" while the device was actually online. (2) On a cold open or after the app was backgrounded for a while, the app took a very long time to load and sometimes landed on a full-screen "You're offline" page even when connected. (3) On the daily checklist, the freezer temperature field couldn't accept negative numbers — the Android decimal keypad has no minus key, so the user could only type positive numbers.
**Root cause:**
1. [useOnlineStatus.ts](src/hooks/useOnlineStatus.ts) returned `navigator.onLine` directly. That signal is well-known to false-positive on Android Chrome during cellular handoffs, radio sleep, brief DNS hiccups, and just after waking the tab from background — it can flip to `false` for several seconds while the device is fine. The OfflineBanner was therefore showing "offline" any time those transient flips occurred.
2. BUG-045 added a 15s navigation timeout to the SW that falls back to `/offline.html`. On a cold open with a sleeping radio, the first navigation fetch routinely takes 10–20s; 15s was right on the borderline, so slow-but-connected cold opens were tripping the fallback. The fallback page was also titled "You're offline" — a misleading message when the real cause was just a slow first packet, not lack of connectivity.
3. [checklist/page.tsx](src/app/(app)/checklist/page.tsx) freezer temp input used `<input type="number" inputMode="decimal">`. Android's decimal keypad does NOT include a minus key in any of the common keyboard implementations (Gboard, SwiftKey, Samsung). The schema (`tempField` in [schemas.ts](src/lib/validation/schemas.ts)) and DB column already accepted -99.9..99.9 — the bug was purely in the input affordance.
**Fix:**
1. `useOnlineStatus` is now probe-based: the `online` event still flips state immediately to true, but the `offline` event is debounced 1.5s and confirmed by a HEAD probe to `/manifest.json` (an unauthenticated static asset that always serves and is intentionally in the SW's `NEVER_CACHE_PATHS` list). Only declare offline if the probe ALSO fails. Visibility-change probes once on tab focus so an Android device returning from backgrounding gets the correct state even if the OS suppressed online/offline events while the tab was hidden.
2. SW navigation timeout bumped 15s → 25s in [public/sw.js](public/sw.js) (SW cache v59 → v60); [offline.html](public/offline.html) reworded from "You're offline / This page isn't available offline yet" to "Reconnecting… / Your connection is slow or your phone's network just woke up" with an auto-reload after 6s so the user doesn't have to tap to recover from a transient stall. The 25s+6s combination covers ~37s of "slow network" automatically before the user has to intervene.
3. Freezer field is now a sign-toggle button next to a positive-only number input. The toggle button shows "Below zero" (filled brand teal, default) or "Above zero" (gray outline); tapping flips the sign. The number input is `type="number" min="0" inputMode="decimal"` and any leading `-` typed on desktop is stripped on change. On save, the stored value is `(sign === '-' ? -1 : 1) * Math.abs(number)`. On load, the existing value's sign is split into the toggle state and absolute value. Fridge field (which is always positive) unchanged. 5 new i18n keys × 5 locales (native translations for so/zu/am/ur; parity green).
**Prevention rule:** (a) Never trust `navigator.onLine === false` as authoritative on mobile. To decide whether to display "offline" UI, debounce the offline event and confirm with a real network probe (HEAD/GET against a static asset). The `online` event in the other direction is safer to trust immediately. (b) When a service-worker navigation fallback page exists, its copy must accurately describe the cause of falling back. A 25s timeout firing because the radio was suspended is "slow connection," not "offline" — using the offline message anywhere except a real-offline path will confuse users. Pair the timeout with auto-reload so transient stalls self-recover. (c) On Android, `inputMode="decimal"` keyboards do not include a minus key. Any numeric field that must accept negatives (freezer temps, debits, deltas) MUST provide a sign affordance separate from the keypad — typically a sign toggle button. Reserve `type="number" inputMode="decimal"` for fields that are always non-negative.

## BUG-047: Teller redirect loop (`ERR_TOO_MANY_REDIRECTS`) — subscription gate vs teller enforcement
**Symptom:** A teller who logged in got "This page isn't working — too many redirects." Owners logged in fine. Surfaced after a batch of deploys (CSP nonce migration, then Upstash rate limiting) finally went live via a forced deploy.
**Initial misdiagnosis (kept on record):** The CSP nonce migration (commit d0850ec) was suspected first — it had changed `proxy.ts` to forward a custom headers clone (`NextResponse.next({ request: { headers } })`) instead of Supabase's canonical `NextResponse.next({ request })`, which can break cookie propagation to the RSC `getUser()`. That migration was reverted (the nonce work is genuinely risky and belonged on a preview branch anyway — see prevention (e)). **But the teller loop persisted after the revert**, proving the nonce migration was NOT the cause.
**Actual root cause:** A structural conflict between two pre-existing redirect rules in `proxy.ts`. (1) The **subscription gate** (`if (role && !isExempt)`) applied to **all roles including tellers**. A teller's JWT does not carry the shop's `sub_until`, so after the `268cf9e` gate hardening (empty/missing `sub_until` on a non-active status ⇒ treated as expired), the gate redirected the teller to `/subscribe`. (2) **Teller route enforcement** runs earlier and only permits `TELLER_ALWAYS_ALLOWED` / `TELLER_GRANTED_ONLY` paths — `/subscribe` is on neither, so a teller landing there is immediately bounced to `/sale`. Net: `/sale →(sub gate)→ /subscribe →(teller enforcement)→ /sale → …` infinite loop. It bit **paid** shops too: the shop subscription was valid (owner reached the dashboard), but the teller's JWT lacked the sub status, so the gate still saw "expired" for the teller.
**Fix:** Subscription gate now applies to **owners only** — changed `if (role && !isExempt)` to `if (role === 'owner' && !isExempt)`. Admins already returned earlier; tellers now fall through to normal access. Tellers can't subscribe (no billing identity), so gating them was never meaningful. SW cache v65 → v66. **Known trade-off (flagged to user):** a teller of a genuinely *expired* shop can now still reach `/sale` (the owner is still blocked at `/subscribe`, which is the real payment pressure). Strict teller lockout on expiry would need a dedicated teller-facing "shop suspended" screen — deliberately not built here to avoid introducing another redirect target; revisit if strict enforcement is wanted.
**Prevention rule:** (a) Before redirecting a role to a destination, verify that role is actually *allowed* to land there. The subscription gate sent tellers to `/subscribe`, a path teller enforcement forbids — any redirect target must be reachable by the role being redirected, or you get a loop. (b) A "redirect target must be in the allow-list" invariant is worth a test: for each role, assert every path the proxy can *redirect that role to* is one the proxy lets that role *stay on*. (c) Role-scoped gates should name the role explicitly (`role === 'owner'`), not a truthy `if (role && …)` check, when the concept applies to one role — the truthy check silently swept in tellers. (d) Confirm a fix actually clears the symptom before recording the root cause; the first plausible suspect (the nonce migration) was wrong, and reverting it cost a cycle. (e) Middleware/auth/routing changes can't be validated by `tsc` + unit tests + `next build` alone (none exercise the authenticated render path) — browser-test owner AND teller login on a preview deploy. The CSP nonce work, when retried, must go on a preview branch for this reason.

**Follow-up (2026-05-30) — closed the known trade-off: strict teller lockout via `/shop-suspended`.** Tellers of a genuinely *expired* shop are now blocked from the app and shown a dedicated "Subscription ended — ask the shop owner to resubscribe" screen, WITHOUT re-introducing the loop. How the two BUG-047 traps were avoided: (1) **Never redirect a teller to a path teller-enforcement forbids** — the new `/shop-suspended` route is added to `TELLER_ALWAYS_ALLOWED` (asserted by a new `tests/unit/route-access.test.ts`), and the page itself never redirects toward a teller-forbidden path. (2) **Never decide "expired" for a teller from the teller's JWT** (it has no `sub_until`; "missing = expired" is what locked out paid shops) — the teller check reads the **live `shops` row** via the existing `React.cache`'d `getShopForRequest()` (no extra query). **Structure that makes it loop-proof:** `/shop-suspended` is a **top-level route OUTSIDE the `(app)` group**, so the `(app)/layout.tsx` teller-expiry redirect to it does NOT re-enter that layout — there's no second redirect to bounce against. The page is **self-healing**: it re-reads the live shop and, if the sub is active again (owner resubscribed), redirects the teller back to `/sale`. Expired→stay on `/shop-suspended`, active→`/sale`: each shop state redirects in exactly one direction, so no oscillation is possible. **Single source of truth:** the new pure `src/lib/subscription/expiry.ts` (`isSubscriptionExpired` + `subscriptionEndDate`) is used by BOTH the owner gate (refactored to call it, no behaviour change) AND the teller check, so the two can't drift — covered by `tests/unit/subscription-expiry.test.ts`. Route allow-lists moved out of `proxy.ts` into `src/lib/auth/route-access.ts` so the reachability invariant is testable without importing edge code. SW cache v67 → v68. **Still requires a browser test on a preview deploy** (per prevention (e)): active-shop teller → `/sale` (no loop); expired-shop teller → `/shop-suspended` (can't reach `/sale` or `/stock-take`); expired owner → still `/subscribe`; resubscribe → teller's next nav unlocks.
